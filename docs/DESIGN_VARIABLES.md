# Design variables

Pro mode shows a separate Design variables group. Each numeric row displays its current value and its effective origin: setup global, test, or top cell. Only the selected Test participates. Enabled Global scope overrides its Test and top-cell defaults; disabled Global participation is not promoted by catalogue discovery. Known numeric formulas can be selected with an explicit domain; they retain a pending native-point proof and receive no fabricated default seed. Non-numeric and multi-valued rows cannot become optimization axes.

The selected design-variable identities retain `source_kind` (`global` or `top`), `variable_source` and `variable_test`. Device-only configurations and historical checkpoint fingerprints keep their previous meaning. Runs selecting design controls freeze `crescendo.design_variables.v1`; their checkpoint manifest independently records the exact selected source/Test identities. Mixed native plans use `crescendo.native_parameter_plan.v2`; existing device-only plans retain v1.

Before optimizer ask, an unchanged native capture resolves selected device expressions with the shared lexical scope and property-alias resolver. Selected design variables take priority: dependent device axes are removed, and the run log plus `design_variable_priority.json` record `variable -> device/property`, the exact declaration identity and per-corner netlist evidence. Unsupported or ambiguous alias/instance bindings fail qualification. Local same-name declarations do not create a dependency on an unrelated top declaration.

Native Run writes scalar Global values with the XL equivalent `ocnxlSweepVar` and reads them back from the native variable handle. Generation batching uses `ocnxlSweepVar` columns in an actual native variableset. IC618 requires at least two set members, so a single axis gets one collision-checked constant companion column; it adds no optimizer dimension. For mixed Global/device axes, device fields are bound to exact owned Global aliases and all Global columns join one `ocnxlParametricSet`. The getter, membership/enable, native condition, corner and per-device SCS proofs remain mandatory. Device-only batches retain their P2 parameter sets. Maestro Netlist applies the same native controls before capture. Template Netlist replaces only the proven top declaration value with an owned candidate symbol, then checks numeric/low/high native references and every dependent assignment. Every point must emit the requested top parameter; duplicate definitions, missing declarations or unsupported shadowing fail closed.

The Parameters page shows an advisory in Simple and Pro when more than 50 variables are selected (`VARIABLE_NOTICE_THRESHOLD`). Device parameters, Global and top design variables, and each linked member count individually. At startup, the GUI, CLI, and headless runner log a WARN with the threshold and the effective count after design-variable priority is applied. Diagnostic reports include the same WARN. You can start a run with any selection size.

In Native Run and Maestro Netlist, consider narrowing the selection to reduce both the time per generation and the number of generations needed to converge. In some environments, Virtuoso can quit unexpectedly during Template Netlist reference capture with many variables. If this happens, select fewer variables or switch to Maestro Netlist or Native Run. The run repeats this advice after the first cause when a reference capture crash ends a run over the threshold.

Global and Local active source variables must still have one value. Multiple values belong in corners. An enabled corner defining a selected design control is a conflict; the error names both the corner and variable. Candidate-only expected values do not change the saved source contract or relax checks on other variables.

Diagnostics validate the original frozen candidate and plan before qualification. When priority removes device dimensions, they project every planned point onto the surviving variables without sampling again or changing point order. Effective candidate/plan hashes are saved with the run. Diagnostic verification and focused cross-mode checks use this qualified plan, reject inconsistent projections between modes, and report its actual distinct/repeated counts; the original shared request remains frozen for each launch.
